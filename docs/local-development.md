# Local development

The repository is a pnpm workspace. Use Node.js 24 or newer and pnpm 10. The
checked-in `.nvmrc` is the reference Node version. All examples use the
synthetic fixture under `fixtures/vault/`; never point local commands at a
personal vault or real deployment.

## Repository checks

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm validate
```

`fs-xattr` and `macos-alias` are intentionally excluded from ordinary pnpm
lifecycle builds because native `node-gyp` diagnostics may expose the ambient
process environment. `pnpm ignored-builds` must list both as explicitly
ignored. The DMG command rebuilds only those two packages immediately before
Forge, through an allowlisted environment with suppressed child output.

The aggregate command is `pnpm check`. `pnpm validate:compose` validates the
non-deployable runtime contract statically and runs `docker compose config`
when the CLI is available. A missing Docker daemon is a warning, not a
container smoke test.

```sh
node scripts/validate-compose.mjs deploy/runtime/compose.contract.yaml --strict
node scripts/validate-compose.mjs deploy/compose.example.yaml --allow-local-example
```

The contract fixture contains synthetic IDs and relative fixture paths only.
Production Compose is generated by `@vault-mcp-bridge/deployment`; do not copy
the fixture into a real host. The generated runtime has two long-running
containers (`server` and `tunnel`) plus two network-disabled one-shot
secret-init jobs. SSH/SFTP-uploaded file-source secrets are `0600`; init jobs copy
them into per-runtime named volumes with exact UID/GID and configured copy mode
(default `0440`), and long-running services mount only their own volume
read-only.

## Normal desktop surface

The product development surface is the Electron app. It is one launch and
does not start a localhost renderer server:

```sh
pnpm dev
pnpm dev:desktop
pnpm --filter @vault-mcp-bridge/desktop build
pnpm --filter @vault-mcp-bridge/desktop start
pnpm --filter @vault-mcp-bridge/desktop test
```

The native folder picker selects `fixtures/vault/`; the server sheet accepts a
synthetic Linux target or a test SSH alias. The renderer is loaded from the
`vaultbridge://app` origin with sandboxing, context isolation, disabled Node
integration, and an explicit IPC allowlist. The packaged app constructs the
production coordinator and fails closed until valid public product
configuration is present; `LocalDesktopBackend` remains only a test harness.
On launch, a configured backend restores its persisted orchestrator record,
retries resumable setup when appropriate, and schedules background sync after
`ready`; the scheduler never opens SSH. Do not interpret a local harness as a
deployed VPS or connected ChatGPT account.

Non-secret desktop configuration may be supplied by a JSON file or the exact
`VAULT_BRIDGE_*` environment names in `apps/desktop/src/product-config.ts`:
`VAULT_BRIDGE_EDGE_ORIGIN`, `VAULT_BRIDGE_OWNER_ISSUER`,
`VAULT_BRIDGE_OWNER_AUTHORIZATION_ENDPOINT`,
`VAULT_BRIDGE_OWNER_TOKEN_ENDPOINT`, `VAULT_BRIDGE_OWNER_JWKS_URI`,
`VAULT_BRIDGE_OWNER_AUDIENCE`, `VAULT_BRIDGE_OWNER_CLIENT_ID`, optional
`VAULT_BRIDGE_OWNER_SCOPE`, `VAULT_BRIDGE_SERVER_IMAGE_REPOSITORY`,
`VAULT_BRIDGE_SERVER_IMAGE_DIGEST`, `VAULT_BRIDGE_TUNNEL_IMAGE_REPOSITORY`,
`VAULT_BRIDGE_TUNNEL_IMAGE_DIGEST`, optional
`VAULT_BRIDGE_RUNTIME_MODE`, `VAULT_BRIDGE_INSTALLATION_DIRECTORY`, and
`VAULT_BRIDGE_SYNC_INTERVAL_MINUTES`. Use HTTPS-shaped synthetic URLs and
`sha256:` placeholders for local tests; tokens and private keys belong in the
safe-storage/Keychain adapters.

The packaged app resolves this non-secret configuration in a fixed order:
environment variables first, then `product-config.json` in the Electron
`userData` directory, then `product-config.json` beside packaged resources
(`process.resourcesPath`). A Forge build embeds a public configuration file
only when `VAULT_BRIDGE_PRODUCT_CONFIG_PATH` names a file ending exactly in
`product-config.json`; it never embeds tokens, private keys, or lease material.
Without real managed-edge/OIDC/image-digest inputs the current release
candidate intentionally remains unconfigured. A clean-install one-launch
claim requires a configured packaged smoke test; local source tests do not
prove it.

The desktop's managed-installation seam generates the publisher mTLS private
key and PKCS#10 CSR on the Mac. Tests may inject a fake identity provider, but
the private key must never be sent to an edge or written to a fixture.

Unsigned directory/package review is available with:

```sh
pnpm --filter @vault-mcp-bridge/desktop package:dir
pnpm --filter @vault-mcp-bridge/desktop package
```

Signing/notarization requires the CI/Forge credentials described in
[`release-process.md`](release-process.md); do not create or store them in a
local `.env` file.

## Legacy developer harness

`apps/agent` and `apps/server` retain the previous loopback surfaces for
synthetic protocol tests. They are explicitly legacy and are not the normal
owner UX. In particular, the local dashboard's preview/device/pair sequence
and the server pairing-code CLI must not be presented as product onboarding.

Start the harness with the root scripts:

```sh
pnpm dev:legacy:server
pnpm dev:legacy:agent
```

The server defaults to a development loopback listener. Set a disposable,
untracked `MCP_DEV_TOKEN` before testing MCP calls; it is rejected in
production. The agent defaults to loopback (`BRIDGE_HOST=127.0.0.1`,
`BRIDGE_PORT=3210`) and may use loopback HTTP only when explicitly enabled:

```sh
BRIDGE_ALLOW_LOOPBACK_HTTP=1 \
BRIDGE_HOST=127.0.0.1 \
BRIDGE_PORT=3210 \
pnpm dev:legacy:agent
```

`BRIDGE_UNSAFE_DEV=1` is required for any non-loopback agent bind and is never
a production control. The agent's local data directory is outside the vault;
set `BRIDGE_DATA_DIR` only to an untracked, private directory.

For migration tests that exercise the old device protocol, create and revoke
synthetic devices through the server CLI:

```sh
pnpm --filter @vault-mcp-bridge/server pairing-code -- --vault-id <synthetic-id>
pnpm --filter @vault-mcp-bridge/server revoke-device -- --device-id <opaque-id>
```

Do not put a real code, device key, or server URL in docs or logs. Pairing is a
bootstrap protocol property; in the final product the desktop orchestrator
keeps any legacy pairing call internal while obtaining credential leases and
device material without asking the owner to copy a code. If a desktop crash
occurs after a pair is accepted but before local state commits, retrying with a
fresh one-use code for the same installation/vault/public key returns the same
device idempotently. A mismatched or revoked identity fails closed.

## Edge development

The edge package has a deterministic provider for development/test only. Its
origin and issuer remain HTTPS-shaped in the contract, even when the local
adapter permits HTTP:

```sh
EDGE_ORIGIN=https://edge.example.test \
EDGE_ISSUER=https://edge.example.test \
EDGE_DEV_OWNER_TOKEN=replace-with-an-untracked-disposable-value \
EDGE_DEV_OWNER_ID=synthetic-owner \
pnpm dev:edge
```

The edge accepts `EDGE_MODE=managed` or `EDGE_MODE=self-hosted` and binds to
`EDGE_BIND_HOST`/`EDGE_BIND_PORT` (defaults `127.0.0.1:8790`). A production edge
requires owner-browser OIDC `EDGE_OWNER_ISSUER`, `EDGE_OWNER_AUDIENCE`,
`EDGE_OWNER_JWKS`, `EDGE_OWNER_AUTHORIZATION_URL`, `EDGE_OWNER_CLIENT_ID`, and
`EDGE_OWNER_TOKEN_ENDPOINT`; file-backed `EDGE_STATE_FILE`,
`EDGE_CREDENTIAL_VAULT_FILE`, `EDGE_CREDENTIAL_MASTER_KEY_FILE`; and the
Cloudflare settings `EDGE_PROVIDER=cloudflare`,
`EDGE_CLOUDFLARE_API_TOKEN_FILE`, `EDGE_CLOUDFLARE_ACCOUNT_ID`,
`EDGE_CLOUDFLARE_ZONE_ID`, `EDGE_CLOUDFLARE_ZONE_NAME`. The production edge
loads one stable OAuth signer from the encrypted vault and must run one process
per state file. Deterministic owner auth/provider credentials are not
production evidence; Cloudflare `rotate` is intentionally fail-closed.

## Local server configuration

`.env.example` is a name-only development template. Copy it to an untracked
file only after reviewing the threat model. Useful synthetic settings include
`NODE_ENV=development`, `SERVER_HOST=127.0.0.1`, `SERVER_PORT=8787`,
`SERVER_DATABASE_PATH=.data/vault-mcp-bridge.sqlite`, `MCP_HOSTS`,
`PUBLISHER_HOSTS`, and bounded `MAX_*` limits. Production requires
`JWT_ISSUER`, `JWT_AUDIENCE`, offline `JWT_JWKS_FILE`/`JWT_JWKS_JSON`,
installation/resource bindings, distinct hosts, `PUBLISHER_MTLS_REQUIRED=true`,
`PUBLISHER_EDGE_ATTESTATION_SECRET_FILE`, and the distinct
`MCP_EDGE_ATTESTATION_SECRET_FILE`, `MCP_EDGE_ATTESTATION_HEADER`,
`MCP_EDGE_TIMESTAMP_HEADER`, `MCP_EDGE_NONCE_HEADER`, and bounded
`MAX_MCP_EDGE_ATTESTATION_ENTRIES`; the managed MCP Worker performs uncached
online introspection and returns `503` on edge outage before adding its HMAC
proof. See
[`production-deployment.md`](production-deployment.md).

## Focused tests and evidence

Package tests can run independently:

```sh
pnpm --filter @vault-mcp-bridge/desktop test
pnpm --filter @vault-mcp-bridge/server test
pnpm --filter @vault-mcp-bridge/edge test
pnpm --filter @vault-mcp-bridge/agent test
pnpm --filter @vault-mcp-bridge/orchestrator test
pnpm --filter @vault-mcp-bridge/deployment test
```

Use synthetic fixtures for L0–L2 evidence. A passing local test proves neither
Docker isolation nor a real VPS/Cloudflare edge/ChatGPT integration. Dynamic
`/readyz` checks storage and offline-authentication freshness on each request;
the managed MCP Worker separately checks online edge introspection and fails
closed with `503` when that decision is unavailable. Exercise those behaviors
only in a configured container/edge environment (L3/L4 evidence), not as a
source-test claim. Edge and server rate guards are per-process; no global
distributed limit is guaranteed.
Record commands,
commit, environment class, pass/fail boundary, and next action in a redacted
receipt; never include secrets, note text, raw queries, or unredacted paths.
